# Проверка производительности снега

Дата: 22 октября 2026 года.

После исправлений 28 из 28 сценариев со снегом прошли проверку ровного кадрового интервала: без пауз длиннее 25 мс и с p99 не выше 20 мс. Точные показатели приведены ниже. Это проверка CPU throttling в Chrome, не тест на физическом слабом телефоне.

## Что исправлено

Старый ограничитель иногда пропускал доступный кадр из-за расхождения его фазы с кадровыми метками браузера. В контрольном 12-секундном прогоне при ×6 мобильный модуль пропустил один кадр: максимальный интервал составил 33,3 мс, хотя кадровый цикл браузера продолжался без пауз. Та же ошибка повторилась на полном стенде.

Теперь около 60 Hz модуль следует каждому кадру дисплея. Ограничение примерно до 60 FPS применяется к повышенной частоте дисплея. Регрессионные тесты проверяют 59.94/60/60.1/61 Hz без искусственных пропусков и 75/90/120/144 Hz с ограничением около 60 отрисовок в секунду.

Второе исправление относится к контролам. При CPU ×10, 400 точках и постоянном изменении ветра старый обработчик дал две паузы по 33,3 мс за 30 секунд. Теперь меняется только затронутый контрол. Активный Canvas получает настройки на следующем запланированном кадре, без лишних синхронных перерисовок и сброса часов. Сохранение выполняется при отпускании ползунка либо через 180 мс после последнего изменения.

## Метод

- Google Chrome 156.0.8078.48, headless. Компьютер: Apple M2 Ultra, arm64.
- CPU ×1/×4/×6/×10 через CDP `Emulation.setCPUThrottlingRate`. Замедляется работа браузера, скорость падения снега не меняется.
- Модуль: мобильный viewport 393 × 852, DPR 3, Canvas 393 × 852. Контролы и прочий интерфейс стенда отсутствуют.
- Полный стенд: 1280 × 900, два одновременно работающих Canvas. Дополнительно проверен мобильный viewport 393 × 852, DPR 3.
- Матрица: 30 сценариев по 8 секунд после 2 секунд прогрева, включая страницы с полностью выключенным снегом.
- Длительная проверка: 5 сценариев по 30 секунд. Проверены непрерывные изменения ветра через обработчик контрола 10 раз в секунду, а затем отдельный сценарий с паузами и сохранением по окончании жеста.
- Отдельно записывается кадровый цикл браузера и метки реальных вызовов Canvas. Поэтому частота назначенных callbacks не подменяет частоту отрисовки эффекта.
- Считаются средняя частота, минимум в скользящем окне 1 с с шагом 100 мс, p95/p99 и максимум интервала кадров, паузы >25/>50 мс. Наблюдаемый кадр: отправка команд Canvas, а не измерение физического показа пикселей дисплеем.
- CPU p95 включает расчёт и отправку команд для всех активных экранов за один callback. Растеризация и композиция GPU в этот показатель не входят. На замеры добавляется небольшая нагрузка самого счётчика.

## Границы результата

Chrome замедляет CPU относительно этого компьютера. Такой коэффициент не определяет конкретную модель телефона. Другую архитектуру процессора, слабый GPU, нагрев и энергосбережение этот тест не воспроизводит. Это ограничение описано в [документации Chrome DevTools](https://developer.chrome.com/docs/devtools/performance/reference#throttle-the-cpu-while-recording). Для обещания стабильных 60 FPS на конкретном слабом устройстве нужен прогон на этом устройстве.
